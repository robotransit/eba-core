# ADR-045: Formal Telemetry Schema and Observability Contract

**Status:** Proposed
**Date:** 2026-03-30
**Scope:** v0.3.0 (Architecture Hardening)
**Depends on:** ADR-042 (Execution Boundary), ADR-038 (Policy Gate), ADR-039 (Agent Loop)

---

## Context

The Epistemic Control Kernel (ECK) now enforces a deterministic execution structure:

```text
propose_execution → PolicyGate.evaluate → authorize_and_perform
```

This structure is mechanically enforced (ADR-042). However, observability remains:

* loosely structured (logging via `extra={}`)
* inconsistently correlated (task_id + timestamp)
* not formally specified or versioned

v0.4.0 requires empirical validation, which depends on:

* deterministic, structured telemetry
* reliable per-step correlation
* explicit visibility into execution phases

This ADR defines a **formal telemetry schema and emission contract** that:

* reflects the locked execution model
* preserves all global invariants (no authority, no coupling)
* enables deterministic, auditable analysis

---

## Decision

Telemetry in ECK is defined as a **structured, versioned, deterministic event stream** with:

1. A canonical **event envelope**
2. A finite **event type taxonomy**
3. A stdlib-only **telemetry module (`eck/telemetry.py`)**
4. A machine-readable schema and human-readable catalog

Telemetry is **observability-only** and MUST NOT influence behavior.

---

## 1. Event Envelope (Canonical Structure)

All telemetry events MUST conform to the following envelope:

```python
{
    "event_type": str,
    "version": str,
    "timestamp": float,
    "trace_id": str,
    "step_id": str,
    "deterministic_nonce": int,
    "severity": str,
    "source": str,
    "payload": dict,
}
```

### Field Definitions

* **event_type**
  Canonical event name (see taxonomy below)

* **version**
  Schema version (e.g. `"1.0"`)

* **timestamp**
  Wall-clock time (float, seconds since epoch)
  **Observational only — MUST NOT be used for ordering logic**

* **trace_id**
  Identifier for a full agent run

  **Generation semantics:**

  * MAY be supplied by the caller
  * MAY be generated internally at run start
  * If generated internally, nondeterminism (e.g. UUID) is permitted
  * MUST be treated as observational metadata only
  * MUST NOT influence control flow, ordering, or replay semantics

* **step_id**
  Identifier for a single `step()` cycle

  **Generation semantics:**

  * MUST be deterministically derived from kernel state
  * MUST uniquely identify a step within a trace
  * MUST be stable across all events within a step
  * MUST NOT rely on randomness

  **Recommended construction:**

  ```text
  step_id = f"{trace_id}:step:{deterministic_nonce}"
  ```

* **deterministic_nonce**
  Monotonic integer derived exclusively from kernel state progression (e.g. cycle counter)

  **Constraints:**

  * MUST be deterministic
  * MUST NOT depend on time or randomness
  * MUST strictly increase within a trace

* **severity**
  One of: `"DEBUG"`, `"INFO"`, `"WARNING"`, `"ERROR"`

* **source**
  Component emitting the event (e.g. `"agent"`, `"policy_gate"`, `"execution"`)

* **payload**
  Event-specific structured data

---

## 2. Event Type Taxonomy

Telemetry uses a finite, stable set of event types:

### Core lifecycle events

* `step.start`
* `step.end`

### Execution boundary phases (ADR-042 aligned)

* `action.proposed`
* `policy.evaluate`
* `action.executed`

### Epistemic layer

* `epistemic.signal`

### Notes

* Event types MUST be stable and versioned via the schema
* New event types require ADR update or version bump
* Naming convention: `domain.action`

---

## 3. Event Payload Expectations

Full payload definitions are specified in `telemetry/event_catalog.md`.

This ADR defines **minimum semantic expectations** for key events.

### `epistemic.signal`

Represents the epistemic update for a cycle.

Payload MUST include, at minimum:

* `confidence`: float in [0.0, 1.0]
* `category`: critic outcome category — MUST be one of
  `"success"`, `"failure"`, `"partial"`, `"rejected"`, `"deferred"`
  (as defined in `CriticOutcome`)
* `severity`: float in [0.0, 1.0] (if applicable)
* `updated`: bool indicating whether a confidence update occurred this cycle

Additional fields MAY be included as defined in the event catalog.

## 4. Telemetry Module (`eck/telemetry.py`)

### Responsibilities

* Construct validated event envelopes
* Emit telemetry via existing logging infrastructure
* Maintain backwards compatibility with current logging

### Core interface (conceptual)

```python
def emit_event(
    event_type: str,
    *,
    trace_id: str,
    step_id: str,
    deterministic_nonce: int,
    severity: str,
    source: str,
    payload: dict,
) -> None:
    ...
```

### Backwards compatibility

* Existing logging calls using `extra={}` remain valid
* Telemetry is injected under a reserved key:

```python
extra = {
    "telemetry_event": {...envelope...}
}
```

* No existing call sites are required to change

---

## 5. Redaction Hook (PII Control)

The telemetry module MUST expose an optional:

```python
redact_hook: Callable[[dict], dict] | None
```

### Behavior

* If provided, `payload` is passed through `redact_hook`
* The returned payload is emitted
* If not provided, payload is emitted unchanged

### Constraints

* Redaction is user-supplied
* Kernel MUST NOT implement domain-specific scrubbing logic
* Redaction MUST NOT affect control flow or behavior

## 7. Invariants and Constraints

### Observability-only (global invariant)

Telemetry MUST:

* have **no behavioral authority**
* introduce **no control coupling**
* not influence:

  * policy decisions
  * execution paths
  * confidence updates

---

### Determinism preservation

* `deterministic_nonce` MUST be derived from kernel state only
* `step_id` MUST be deterministic
* telemetry MUST NOT introduce nondeterminism into execution behavior

---

### No side effects beyond logging

Telemetry MUST NOT:

* perform network calls
* write to external systems
* mutate external state

All exporters are external packages.

---

### Optional dependency boundary

* `eck/telemetry.py` is stdlib-only
* exporters (e.g. OTLP) live outside the core package

---

## 8. Rationale

### Why a formal envelope?

Without a canonical structure:

* correlation is fragile
* event interpretation is inconsistent
* automated analysis is unreliable

---

### Why `step_id`?

`task_id + timestamp` is insufficient:

* multiple events per step
* ambiguous grouping
* no guaranteed correlation

`step_id` provides explicit step-level grouping.

---

### Why `deterministic_nonce`?

ECK enforces deterministic control flow.

Telemetry must preserve:

* replayability
* stable ordering independent of time

---

### Why `trace_id` flexibility?

`trace_id` is:

* a correlation identifier
* not part of control logic

Allowing external or nondeterministic generation:

* supports integration scenarios
* preserves architectural invariants

---

### Why stdlib-only core?

Maintains invariant:

> Core must remain dependency-free and deterministic

---

### Why redact_hook?

* PII handling is domain-specific
* kernel must remain policy-agnostic
* integrators retain control

---

## 9. Non-Goals

This ADR does NOT define:

* telemetry exporters (OTLP, Kafka, etc.)
* sampling strategies
* retention policies
* compliance frameworks
* visualization or dashboards

These are deferred to v0.4.0+.

---

## 10. Implementation Plan

Instrumentation order reflects **runtime execution sequence**, not priority:

1. `step.start`
2. `action.proposed`
3. `policy.evaluate`
4. `action.executed`
5. `epistemic.signal`
6. `step.end`

Implementation steps:

1. Implement `eck/telemetry.py`
2. Add envelope construction and validation
3. Wrap logging via `telemetry_event`
4. Add schema JSON
5. Add event catalog
6. Incrementally instrument components

---

## 11. Consequences

### Positive

* deterministic, structured observability
* enables v0.4.0 empirical validation
* auditable policy decisions
* stable integration surface

### Negative

* added implementation complexity
* schema versioning discipline required
* small runtime overhead

---

## Final Statement

Telemetry in ECK is:

> **a deterministic, structured, non-authoritative observation layer**

It exists to make the system:

* measurable
* auditable
* analyzable

without ever becoming part of the control surface.

This preserves the core invariant:

> **Information flows in; authority flows only through the policy gate and execution boundary.**
