# ADR-020: v0.2.0 Roadmap and Safety Boundaries

## A. ORDERING (TODO as agenda, but dependency-aware)

### A1) Confidence signal (EWMA / rolling confidence) — first

**WHY FIRST:**  
Confidence becomes an input to several other decisions (policy upgrades, breadth, drift). If we build memory features first, we risk retrofitting confidence semantics around them.

**DESIGN DELIVERABLES (no code):**  
- Define the state machine for confidence updates (inputs, update cadence, reset rules).  
- Define EWMA parameters + failure asymmetry semantics as first-class invariants (not “magic constants”).  
- Decide: is confidence updated per task, per step, or per evaluation?

**MUST NEVER HAPPEN (hard invariant):**  
- Confidence must not become “correctness probability”.  
- Confidence changes must not directly enforce behavior without policy gate mediation.

**OPTIONAL VS CORE:**  
- **Core:** deterministic update semantics.  
- **Optional:** persistence across runs (if ever added later).

**Note:** Confidence Semantics (ADR-021–025) now feed into the Policy Gate (ADR-038), which forms the exclusive decision boundary between epistemic signals and control decisions.

---

### A2) Policy Gate Contract — second

**WHY SECOND:**  
Once confidence semantics are defined, the policy gate defines the exclusive decision boundary where epistemic signals are converted into control decisions.

**DESIGN DELIVERABLES:**  
- Define the minimal contract for the policy gate as the sole consumer of confidence for control (ADR-038).  
- Lock invariants: determinism, side-effect freedom, monotonicity, explicit default semantics.  
- Establish startup-only selection and single active gate.  
- Define the policy gate as the pre-execution authorization boundary that produces execution modes (EXECUTE, RETRY, DEGRADE, HALT).

**MUST NEVER HAPPEN:**  
- Any control decision influenced by confidence without passing through the policy gate.  
- Implicit or runtime gate selection.

**OPTIONAL VS CORE:**  
- **Core:** policy gate contract and default implementation.  
- **Optional:** domain-specific gate implementations.

**Note:** Policy Gate decisions (ADR-038) are enforced by the Agent Loop (ADR-039).

---

### A3) Agent Loop & Policy Gate Integration — third

**WHY THIRD:**  
Once confidence semantics and policy gate are defined, the agent loop must enforce gate decisions at runtime to make them authoritative.

**DESIGN DELIVERABLES:**  
- Define the minimal agent loop that invokes the policy gate exactly once per proposed action before execution (ADR-039).  
- Lock enforcement of all gate modes (EXECUTE, HALT, RETRY, DEGRADE).  
- Ensure no execution path bypasses the gate.

**MUST NEVER HAPPEN:**  
- Execution without prior gate authorization.  
- Multiple or non-deterministic gate evaluations for a single proposed action.  
- Execution of HALT/RETRY/DEGRADE outcomes as if authorized.  
- Ad hoc degraded execution paths not explicitly defined.  
- Post-execution gate enforcement.  
- Retry generation or retry decision-making inside the gate.  
- Implicit retry orchestration not explicitly defined by the surrounding control layer.

**OPTIONAL VS CORE:**  
- **Core:** loop enforcement of policy gate decisions.  
- **Optional:** domain-specific recovery logic.

---

### A4) Memory-aware prediction context “activation wiring” — fourth

**WHY FOURTH:**  
Once confidence semantics, policy gate, and loop enforcement are defined, memory retrieval can be integrated without becoming a covert control surface.

**DESIGN DELIVERABLES:**  
- Define the contract of “memory context”:  
  - It is read-only.  
  - It may influence prediction text, but must not become authority.  
- Define gating:  
  - `enable_memory_retrieval=False` must remain a hard-off switch.  
  - With retrieval enabled, empty results must behave like “no context”.

**MUST NEVER HAPPEN:**  
- Retrieval must never execute when disabled.  
- Adding memory context must not change prompts in “disabled” mode (no drift).

**OPTIONAL VS CORE:**  
- **Core:** retrieval gating + deterministic formatting.  
- **Optional:** negative-memory preference heuristics, scoring variants.

---

### A5) Similarity upgrade (embeddings / cosine) — fifth

**WHY FIFTH:**  
Similarity is a “mechanism” that affects retrieval quality, not semantics. Wire semantics first, upgrade mechanism after.

**DESIGN DELIVERABLES:**  
- Decide which similarity API is authoritative long-term:  
  - `retrieve_similar` vs `retrieve_scored` (or both; define roles).  
- Decide how embedding similarity integrates:  
  - optional dependency, extras, fallback strategy.

**MUST NEVER HAPPEN:**  
- Core package must not become non-stdlib by default.  
- Optional dependency failure must not break the agent.

**OPTIONAL VS CORE:**  
- **Core:** stdlib-only similarity remains available.  
- **Optional:** embeddings + cosine via extras.

---

### A6) Prompts integration cleanup (use or remove) — sixth

**WHY SIXTH:**  
Prompts are “control-plane ergonomics”; integrate only after the big semantics are stable.

**DESIGN DELIVERABLES:**  
- Decide whether `PRIORITIZATION_PROMPT` is:  
  - used for queue ordering, or  
  - deleted to reduce conceptual surface.  
- Confirm `GOAL_ACHIEVED_PROMPT` status:  
  - already used (if so, document as contract), or  
  - unused (then decide: integrate or remove).

**MUST NEVER HAPPEN:**  
- New prompt usage that changes runtime behavior without tests.  
- Hidden reliance on prompt literal strings as API.

---

### A7) CI workflow — last

**WHY LAST:**  
Infra should follow stable v0.2.0 semantics, not lead them.

**MUST NEVER HAPPEN:**  
- CI introducing network/external service dependencies.  
- CI requiring non-stdlib runtime dependencies for core.
