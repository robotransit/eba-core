# ADR-041: Deterministic Goal Completion Semantics

**Status:** Proposed (Target: v0.2.0 reconciliation)

---

## Objective

Define the deterministic predicate for goal completion in the Epistemic Control Kernel (ECK), replacing the current non-compliant LLM-based goal check.

This ADR establishes:

* the authority boundary for lifecycle termination
* the required signals for declaring objective completion
* the invariants governing completion semantics
* the interaction with existing subsystems (critic, confidence, policy, queue)

This ADR fulfills the requirement introduced by ADR-033:

> Lifecycle decisions must not be delegated to unconstrained LLM outputs.

---

## Context

### Current State (Non-Compliant)

The current agent loop determines goal completion via:

BACKTICKS
if "YES" in self.llm(goal_prompt).upper():
return False
BACKTICKS

This is non-compliant because:

* it delegates termination authority to a free-form LLM response
* it has no deterministic parsing or schema
* it is vulnerable to prompt variation and ambiguity
* it violates the control boundary defined in ADR-033

---

### Architectural Requirement

Goal completion is a **lifecycle control decision** and must therefore be:

* deterministic
* auditable
* independent of unconstrained LLM output
* derived only from kernel-controlled signals

---

### Available Signals

The kernel already maintains the following relevant signals:

* **Critic outcome** (success/failure/partial)
* **Task queue state** (pending work)
* **Confidence** (epistemic accumulation; ADR-021–025)
* **Policy mode** (execution constraints)
* **Drift state** (error accumulation; ADR-040)

This ADR defines which of these signals are authoritative for goal completion.

---

### Key Design Questions

#### 1. Local Success vs Global Completion

A single task success does not imply objective completion.

Goal completion must reflect:

* global objective satisfaction
* not just local task correctness

---

#### 2. Failure Window Interaction (ADR-023)

During a failure window:

* upward confidence movement is suppressed
* the kernel is explicitly in a cautionary epistemic state

This creates a critical scenario:

* current task succeeds
* queue is empty
* but the kernel is still within a failure window

Question:

> Should the kernel be allowed to declare completion while its epistemic system is still signalling caution?

This motivates inclusion of a confidence floor in the completion predicate.

---

#### 3. Queue-Empty Semantics

“Queue empty” is ambiguous and must be disambiguated.

Two distinct cases exist:

1. **Natural exhaustion**

   * all required work has been completed

2. **Policy-suppressed emptiness**

   * no further work was generated due to policy constraints (e.g. ENFORCED mode)

These are epistemically different:

* natural exhaustion indicates completion
* suppressed emptiness may indicate incomplete exploration

---

#### 4. Confidence Participation

Two valid design options exist:

**Option A: Confidence participates**

* completion requires confidence ≥ threshold

**Option B: Confidence excluded**

* completion based only on critic + work-state signals

This ADR resolves this choice explicitly.

---

## Decision

### 1. Deterministic Completion Predicate

Goal completion MUST be determined by a deterministic predicate composed of:

* critic outcome
* task/work-state
* confidence

LLM outputs MUST NOT directly influence completion.

---

### 2. Required Conditions (Refined)

The kernel declares goal completion if and only if:

1. **Current task is successful**

   * as determined by the critic

2. **No required work remains**

   * the task queue is empty
   * AND subtask generation was not suppressed in the current cycle by policy constraints

3. **Sufficient epistemic confidence**

   * confidence ≥ goal_completion_threshold

---

### 3. Queue Semantics (Locked + Implementation Requirement)

Queue emptiness MUST be interpreted as valid completion **only when naturally exhausted**.

Queue emptiness caused by:

* policy gating
* subtask suppression
* exploration constraints

MUST NOT be treated as sufficient for completion.

#### Implementation Requirement

The kernel MUST be able to distinguish:

* natural exhaustion
* policy-suppressed emptiness

This requires at least one of:

* a per-cycle flag indicating subtask generation suppression
* or an equivalent check against policy gating decisions in the current cycle

Queue state alone is insufficient to determine completion validity.

---

### 4. Confidence Participation (Locked Decision)

**Confidence IS REQUIRED as part of the completion predicate.**

The kernel MUST enforce:

* confidence ≥ goal_completion_threshold

Where:

* goal_completion_threshold is a configurable parameter
* default MAY align with execution threshold (e.g. 0.90)

#### Note

The completion threshold and execution threshold are conceptually distinct and MUST NOT be implicitly coupled, even if they share a default value.

#### Rationale

* prevents premature completion after isolated success
* resolves failure-window inconsistency (ADR-023)
* ensures completion reflects accumulated epistemic confidence

---

### 5. Final Predicate

The canonical completion condition is:

BACKTICKS
task_success
AND no_required_work_remaining
AND confidence >= goal_completion_threshold
BACKTICKS

---

### 6. Authority Boundary

* Critic determines task-level correctness
* Queue/work-state determines completeness of required work
* Confidence determines epistemic sufficiency

No single component has unilateral authority.

---

### 7. Observability Requirements

Goal completion MUST be logged with:

* task_id
* final confidence
* queue state
* policy mode
* critic outcome

Logging MUST be:

* structured
* side-effect free
* consistent with ADR-040

---

## Non-Goals

This ADR does NOT define:

* how subtasks are generated
* how confidence is computed (ADR-021–025)
* how policy gating determines exploration breadth
* specific queue implementation details

---

## Consequences

### Positive

* eliminates non-deterministic lifecycle control
* aligns termination with epistemic state
* preserves auditability and reproducibility
* resolves failure-window inconsistency
* prevents false completion under constrained exploration

---

### Trade-offs

* introduces dependency on confidence calibration
* requires explicit configuration of completion threshold
* may delay completion relative to naive success criteria

---

## Test Requirements

The following tests are mandatory:

### 1. LLM Override Resistance (Compliance Guard)

* deterministic criteria met
* LLM indicates “not complete”

→ kernel MUST complete

*Note: This is a compliance guard test ensuring no implementation reintroduces LLM authority into lifecycle decisions.*

---

### 2. False Positive Resistance (Compliance Guard)

* deterministic criteria NOT met
* LLM indicates “complete”

→ kernel MUST NOT complete

*Note: This is a compliance guard test ensuring LLM output is not consulted by the completion predicate.*

---

### 3. Failure Window Case

* success occurs during failure window
* confidence < threshold

→ kernel MUST NOT complete

---

### 4. Policy-Suppressed Queue (Negative Case)

* queue empty due to policy suppression

→ kernel MUST NOT complete

---

### 5. Natural Exhaustion (Positive Case)

* queue empty due to full completion
* task success
* confidence ≥ threshold

→ kernel MUST complete

---

### 6. Deterministic Replay

* identical inputs and critic outcomes

→ identical completion decision

---

## Compliance

Any implementation that:

* uses LLM output for completion decisions
* ignores queue-state semantics
* omits confidence requirement

is **non-compliant** with this ADR.
