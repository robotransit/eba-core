# ADR-043: Demonstration Policy Module (Childcare Domain — Semantic Capability Proof)

**Status:** Proposed (Revised v6)
**Version:** v0.3.0
**Date:** 2026-03-29

---

## Objective

Define and implement a **demonstration policy module** that proves:

> The ECK architecture can express policy that is **not reducible to confidence**, and can enforce **domain-semantic constraints on execution even at high confidence**.

This module is a **capability proof**, not a production policy.

---

## Scope

This ADR defines:

* A **childcare-domain policy module**
* Explicit structured interpretation of `ProposedAction.parameters`
* Operational use of `PolicyContext.environment` and `PolicyContext.safety_level`
* At least one **high-confidence non-EXECUTE outcome on semantic grounds**
* A test suite enforcing these properties

This ADR **references ADR-044** for out-of-domain behavior and does not redefine it.

---

## Domain Choice and Scope Disclaimer

The childcare domain is chosen because:

* safety stakes are immediately legible to any reader
* “the model was confident” is obviously insufficient justification in a child-facing context
* `PolicyContext.safety_level` and `environment` map naturally to real-world regulatory concepts
* it directly reflects commercially relevant deployment scenarios

This policy is intentionally **not complete**:

* it is not a regulatory or compliance policy
* it is not exhaustive of childcare constraints
* it is a **minimal semantic rule set sufficient to prove architectural expressiveness**

A production childcare policy module would be:

* domain-expert authored
* substantially more comprehensive
* treated as a separate deliverable

---

## Design Principles

### 1. Deterministic and Pure

* No side effects
* No external calls
* No hidden state
* Identical inputs → identical outputs

### 2. Policy as the Sole Behavioral Translator

* Confidence is epistemic only
* Policy determines execution mode

### 3. No Execution Authority

* Returns `PolicyDecision` only
* Does not execute or trigger effects

### 4. Structured Semantic Inspection

* Must inspect structured `ProposedAction.parameters`
* Must not rely on free-form text alone
* Must not reduce to single-field checks

### 5. Contextual Authority

* `environment` defines domain applicability
* `safety_level` modifies behavior within domain

## Demonstration Parameter Schema (Operational Contract)

To make semantic rules concrete, the demonstration module assumes the following minimal structured schema within `ProposedAction.parameters`:

* `audience`: `"child"` | `"adult"`
* `request_kind`: `"inform"` | `"transform"` | `"generate_activity"`
* `bounded`: `bool` — whether the request has explicit constraints or limits

### Required Schema (Non-Optional)

This schema is **mandatory**, not advisory.

A `ProposedAction` evaluated by this module MUST include all required fields. Missing fields indicate a **structurally incomplete proposal for this domain** and must result in a non-EXECUTE decision.

This enforces:

* fail-closed semantics
* auditability of malformed inputs
* the architectural claim that `ProposedAction` is a meaningful semantic object

---

## Domain Semantics

The module represents a **childcare policy module**:

* actions may directly affect children
* unbounded or directive transformations carry elevated risk
* safety context must constrain execution

---

## Evaluation Order (Authoritative)

The policy module MUST evaluate in the following order:

1. Out-of-domain check (ADR-044)
2. Required parameter schema validation
3. Domain semantic rules (Rules 3–4)
4. Failure window check
5. Baseline confidence thresholds

This ordering is **load-bearing** and must not be altered.

---

## Environment Precondition

The module verifies:

```python
context.environment == "childcare"
```

This is a **defensive semantic precondition**, not routing logic.

---

## Policy Rules (Demonstration Set)

### Rule 1 — Out-of-Domain Fallback (ADR-044)

If:

* `context.environment != "childcare"`

Then:

* return non-EXECUTE (e.g. `DEGRADE`)
* `rule_id = "RULE_OUT_OF_DOMAIN"`
* reason explicitly identifies mismatch

---

### Rule 2 — Missing Required Parameters (Fail-Closed)

If:

* any of the required schema fields (`audience`, `request_kind`, `bounded`) are missing

Then:

* return non-EXECUTE
* `rule_id = "RULE_MISSING_PARAMETERS"`
* reason identifies missing fields

This rule:

* is independent of confidence
* enforces schema completeness
* prevents silent fallback to confidence-only behavior

---

### Rule 3 — High Safety Level + Unbounded Generation

If:

* `context.safety_level == "HIGH"`
* AND `parameters["bounded"] == False`

Then:

* return non-EXECUTE (`DEGRADE` or `HALT`)
* independent of confidence

**Note:**
If `context.safety_level` is `None`, it is treated as **unspecified** and does **not** match `"HIGH"`. In this case, the rule does not trigger and evaluation proceeds to subsequent rules.

---

### Rule 4 — Directive Transformation for Child Audience (Core Proof)

If:

* `proposed_action.action_type == "llm_query"`
* AND `parameters["request_kind"] == "transform"`
* AND `parameters["audience"] == "child"`

Then:

* return non-EXECUTE (`DEGRADE` or `HALT`)
* **even if confidence ≥ 0.9**

This rule:

* depends on multiple structured fields
* encodes a semantic relationship
* is not reducible to:

  * threshold
  * blacklist
  * single-field check

This is the **load-bearing rule**.

---

### Rule 5 — Baseline Behavior (Failure Window + Confidence)

If none of the above rules apply:

#### Failure Window Handling (Explicit — Inherited from DefaultPolicyGate)

If:

* `context.failure_window_active == True`

Then:

* return non-EXECUTE consistent with `DefaultPolicyGate` Rule 001
* in the baseline path this yields `HALT` regardless of confidence

#### Confidence Thresholds (Inherited)

Otherwise, apply the same thresholds as `DefaultPolicyGate`:

* confidence < 0.40 → `HALT`
* confidence < 0.70 → `RETRY`
* confidence < 0.90 → `DEGRADE`
* otherwise → `EXECUTE`

---

## Required High-Confidence Non-EXECUTE Case

The module MUST include a case where:

* confidence ≥ 0.9
* decision is non-EXECUTE
* decision ignores confidence magnitude
* decision is derived from structured semantics

## Test Requirements

### 1. Structured Inspection

* Different parameter combinations → different outcomes

### 2. Safety-Level Override

* Same confidence, different `safety_level` → different decisions

### 3. High-Confidence Non-EXECUTE

* confidence ≥ 0.9
* semantic rule triggers non-EXECUTE

### 4. ADR-044 Compliance

* out-of-domain → explicit non-EXECUTE
* stable `rule_id` and reason

### 5. Schema Enforcement

* missing required parameters → non-EXECUTE
* `rule_id = RULE_MISSING_PARAMETERS`
* no fallback to baseline

### 6. Failure Window Consistency

* `failure_window_active == True` → non-EXECUTE (HALT in baseline path)

### 7. Determinism

* identical inputs → identical outputs

## Rationale

This ADR shifts the evaluation question from:

> “Is the architecture clean?”

to:

> “Can the architecture express real policy?”

The childcare domain makes it immediately clear that:

* confidence alone is insufficient
* structured semantics matter
* context must carry authority

---

## Summary

The demonstration childcare policy module proves:

* policy is not reducible to confidence
* structured `ProposedAction` is mandatory, not optional
* `PolicyContext` is operational
* context can override high confidence
* schema completeness is enforced
* failure window semantics remain intact
* out-of-domain behavior is explicit (ADR-044)

This establishes ECK as:

> an architecture capable of hosting real domain policy
