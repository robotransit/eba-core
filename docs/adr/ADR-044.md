# ADR-044: Out-of-Domain Policy Module Evaluation Semantics

**Status:** Proposed
**Version:** v0.3.0
**Date:** 2026-03-29

---

## Objective

Define the required behavior when a **policy module** is evaluated outside its intended domain context.

This ADR answers three architectural questions only:

1. Is out-of-domain evaluation a configuration error, a graceful fallback, or passthrough?
2. Is the fallback behavior part of the `PolicyGate` contract, or left to each module?
3. Does the kernel ensure policy-module/domain matching, or is that an operator concern?

This ADR is intentionally narrow and is meant to be referenced by domain-specific policy ADRs such as the revised ADR-043.

---

## Context

ECK now supports concrete **policy modules** that satisfy the `PolicyGate` Protocol. Domain-specific modules will often be written with an intended deployment context, such as:

* childcare
* banking
* medical
* education

A general architectural question therefore arises:

> What should happen if a domain-specific policy module is evaluated in a context outside the domain it was written for?

This question is **not domain-specific**. It applies to any present or future policy module that relies on `PolicyContext.environment` or equivalent contextual assumptions.

If left unspecified, future modules may diverge arbitrarily:

* some may raise
* some may silently passthrough
* some may degrade
* some may halt

That would weaken auditability and produce inconsistent semantics across policy modules.

---

## Decision

### 1. Out-of-domain evaluation is **not** an invariant violation

Evaluating a policy module outside its intended domain is **not** a kernel invariant breach and must **not** raise by default.

Rationale:

* the module can still evaluate deterministically
* the module can still return a valid `PolicyDecision`
* this is not equivalent to a non-compliant caller violating a kernel red line

Therefore, out-of-domain evaluation is treated as a **policy decision case**, not an exception case.

---

### 2. Out-of-domain evaluation must produce an explicit **non-EXECUTE** decision

When a policy module determines that the current context is outside its intended domain, it must return an explicit **non-EXECUTE** `PolicyDecision`.

Permitted modes:

* `DEGRADE`
* `RETRY`
* `HALT`

`EXECUTE` is not permitted for out-of-domain fallback behavior.

This fallback decision must be:

* deterministic
* side-effect free
* independent of confidence
* explicitly attributable to domain-context mismatch

Rationale:

* safe by default
* auditable
* preserves contextual authority
* prevents silent misdeployment

---

### 3. Transparent passthrough is forbidden

A domain-specific policy module must **not** behave as though no domain policy applies when evaluated outside its intended domain.

In particular, it must not silently defer to confidence-only logic in a way that hides the domain mismatch.

Rationale:

* passthrough masks operator/configuration mistakes
* passthrough weakens the architectural meaning of `PolicyContext`
* passthrough undermines the proof that policy can constrain execution on semantic grounds

---

### 4. The fallback behavior is a **policy-module design rule**, not a kernel routing mechanism

The kernel does **not** match policy modules to environments.

The kernel's responsibility ends at:

* supplying `proposed_action`
* supplying `confidence`
* supplying `PolicyContext`
* consuming the returned `PolicyDecision`

Matching the appropriate policy module to the intended domain remains the responsibility of:

* the operator
* the integrator
* the application layer

However, policy modules must defensively verify relevant domain assumptions through context where appropriate.

Rationale:

* preserves the minimal kernel boundary
* avoids introducing policy routing into the kernel
* keeps the `PolicyGate` contract simple and stable

---

### 5. Out-of-domain decisions must be explicit in audit/telemetry surfaces

When returning an out-of-domain fallback decision, the policy module must emit a distinct:

* `rule_id`
* `reason`

Both must make the domain mismatch explicit and machine-stable.

Example shape:

```
PolicyDecision(
mode=ExecutionMode.DEGRADE,
cause=PolicyCause.DEFAULT,
reason="environment mismatch: expected childcare",
rule_id="RULE_OUT_OF_DOMAIN",
)
```

This requirement exists for audit clarity, deterministic testing, and future telemetry integration.

---

## Contract Implications

This ADR does **not** change the `PolicyGate` Protocol signature.

The `PolicyGate` contract remains:

```
evaluate(proposed_action, confidence, context) -> PolicyDecision
```

This ADR defines an additional semantic expectation for **domain-specific policy modules**:

* if a module depends on domain context,
* and the required domain context is absent or mismatched,
* then it must return explicit non-EXECUTE fallback behavior.

This is a **module-level semantic rule**, not a type-level change to the protocol.

---

## Non-Goals

This ADR does not define:

* how domains are registered
* how modules are selected
* a global routing table
* automatic policy-module/environment matching
* which non-EXECUTE mode (`DEGRADE`, `RETRY`, or `HALT`) every module must choose

The exact fallback mode remains a module-specific decision, provided it is:

* non-EXECUTE
* deterministic
* explicit
* context-mismatch driven

---

## Rationale

This ADR chooses explicit non-EXECUTE fallback over two rejected alternatives:

### Rejected: raise / exception

Too strong.

Out-of-domain evaluation is not inherently a kernel invariant violation. The module can still produce a valid, deterministic decision.

### Rejected: transparent passthrough

Too weak.

Passthrough hides misdeployment, weakens auditability, and undermines the architectural claim that policy can exercise contextual authority independently of confidence.

### Chosen: explicit non-EXECUTE fallback

Best fit for ECK because it is:

* safe
* deterministic
* auditable
* non-epistemic
* side-effect free

---

## Consequences

This ADR establishes a general pattern for future domain-specific policy modules:

* modules may be domain-specific
* modules may defensively inspect `context.environment`
* out-of-domain evaluation is handled explicitly and safely
* the kernel remains policy-agnostic and routing-agnostic

This gives future ADRs a consistent reference point and prevents ad hoc divergence.

---

## Example Application

A dedicated childcare policy module may specify:

* intended domain: `context.environment == "childcare"`
* out-of-domain fallback: `DEGRADE`
* reason/rule_id explicitly identifying the mismatch

ADR-043 may then focus on childcare-specific semantic rules without redefining the general out-of-domain pattern.

---

## Summary

When a domain-specific policy module is evaluated outside its intended domain:

* it must **not raise**
* it must **not silently passthrough**
* it must return an explicit **non-EXECUTE** `PolicyDecision`
* the decision must be independent of confidence
* the kernel does not perform module/domain matching
* the policy module must make the mismatch explicit via stable `rule_id` and `reason`

This preserves safety, determinism, auditability, and contextual authority while keeping the kernel minimal.
