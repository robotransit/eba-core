# ADR-039: Agent Loop & Policy Gate Integration

**Status:** Proposed (v0.2.0 candidate)

**Context**

The policy gate (ADR-038) defines pre-execution control decisions, but without enforcement at the loop level those decisions remain advisory.  
This ADR establishes the minimal agent loop integration that makes the gate authoritative: no execution can occur without gate authorization.

**Decision**

The agent loop must enforce the policy gate as the sole pre-execution authorization boundary.

### Loop Semantics

The deterministic agent loop must:

- Generate or receive a proposed action
- Invoke the policy gate in a deterministic location prior to any execution attempt
- Receive a PolicyDecision
- Enforce the decision:
  - EXECUTE → proceed with the proposed action
  - HALT → terminate this cycle (no action taken)
  - RETRY → discard the proposal and return control to the surrounding orchestration layer to obtain a new proposal
  - DEGRADE → do not execute the current proposal as-is; execution may proceed only via an explicitly defined degraded path; if no degraded path is defined, no execution occurs

No execution path may bypass the gate.

### Invariants

- **Gate Authorization Required**  
  No action may be executed unless the gate returns EXECUTE.  
  No alternative or side-channel execution path is permitted.

- **Deterministic Pre-Execution Invocation**  
  Each proposed action must be evaluated by the policy gate exactly once prior to any execution attempt.  
  The gate must be invoked in a deterministic location before any action is attempted.

- **No Bypass Paths**  
  No hidden or implicit execution flow may exist outside gate enforcement.

- **Pre-Execution Only**  
  Gate evaluation must occur before any action execution or side-effect.

- **Enforcement of All Modes**  
  HALT, RETRY, and DEGRADE must prevent execution of the current proposal.

**Must Never Happen**

- Execution without prior gate authorization
- Execution of HALT, RETRY, or DEGRADE outcomes as if authorized
- Ad hoc degraded execution paths not explicitly defined
- Post-execution gate enforcement
- Retry generation or retry decision-making inside the gate
- Implicit retry orchestration not explicitly defined by the surrounding control layer

**Minimal Contract Sketch**

```python
from typing import Any

from eck.policy_gate import PolicyGate, PolicyDecision, ExecutionMode, PolicyContext


class AgentLoop:
    def __init__(self, policy_gate: PolicyGate):
        self.policy_gate = policy_gate

    def step(
        self,
        proposed_action: Any,
        confidence: float,
        context: PolicyContext
    ) -> None:
        decision: PolicyDecision = self.policy_gate.evaluate(
            proposed_action=proposed_action,
            confidence=confidence,
            context=context
        )

        if decision.mode == ExecutionMode.HALT:
            return  # no action taken

        if decision.mode == ExecutionMode.RETRY:
            return  # proposal discarded

        if decision.mode == ExecutionMode.DEGRADE:
            return  # degraded path defined elsewhere

        if decision.mode == ExecutionMode.EXECUTE:
            # authorized execution (actual code here)
            pass
```

**Consequences**

- Advisory-only semantics are enforced at the execution level
- The kernel remains minimal by adding only the enforcement seam required to make gate decisions authoritative at runtime
- All execution paths are auditable and deterministic
- Domain-specific recovery (retry logic, degrade paths) remains outside the kernel

**Alternatives Considered**

- Post-execution gate check — Rejected (too late; violates pre-execution boundary)
- No gate enforcement — Rejected (violates control invariants)
- Gate inside capability layers — Rejected (silent coupling risk)

**Summary**

This ADR establishes the agent loop as the enforcement point for the policy gate, ensuring no execution occurs without explicit gate authorization. It preserves all core ECK/ESS invariants while keeping the kernel minimal.
