# ADR-035: GitHub Actions CI Workflow Implementation

**Status**  
- LOCKED (semantic invariant for v0.2.0 core)

**Objective**  

Specify the concrete GitHub Actions workflow files, job structure, triggers, commands, and separation logic that implement the two-layer CI contract defined in ADR-034.  

This ADR provides the "how" — actual YAML structure, job names, matrix strategy, and enforcement commands — while strictly adhering to the foundational principles (deterministic core blocking, capability non-blocking, stdlib-only core, no network/external dependencies in core layer).

This ADR is scoped to the implementation phase of A5 in the v0.2.0 roadmap (ADR-020). It builds directly on ADR-034 without reopening its decisions, emergent architectural properties (especially Properties 4, 5, 11, 12), §19 red lines, or prior locked ADRs.

**Decisions**

1. **Workflow Files**
   - `.github/workflows/ci-core.yml` → Deterministic Core Layer (blocking)
   - `.github/workflows/ci-capability.yml` → Capability / Optional Layer (non-blocking)

2. **Core Layer Workflow (ci-core.yml)**
   - **Triggers**: on push and pull_request to main and all release branches
   - **Jobs**:
     - **name**: Core Tests
       - **runs-on**: ubuntu-latest
       - **strategy**:
         ```yaml
         matrix:
           python-version: ['3.10', '3.11', '3.12']
         ```
       - **steps**:
         ```yaml
         - uses: actions/checkout@v4
         - uses: actions/setup-python@v5
           with:
             python-version: ${{ matrix.python-version }}
         - name: Install dependencies
           run: pip install -e ".[test]"   # pytest, pytest-cov only — no extras
         - name: Run deterministic tests
           run: |
             # Markers cover all invariant-critical paths from ADRs:
             # - core: general deterministic invariants
             # - guardrail: ADR-033 no-leakage tests
             # - memory: toggle/equivalence
             # - critic: parsing, pessimistic failure
             # - policy: mode irreversibility
             # - queue: deterministic ordering
             pytest \
               -m "core or guardrail or memory or critic or policy or queue" \
               --cov=eck --cov-report=xml --cov-report=html --cov-fail-under=95 \
               --strict-markers --tb=short
         - name: Upload coverage artifacts
           uses: actions/upload-artifact@v4
           with:
             name: core-coverage-${{ matrix.python-version }}
             path: htmlcov/
             retention-days: 7
         ```
   - **Enforcement**: Job fails → PR/merge blocked

3. **Capability Layer Workflow (ci-capability.yml)**
   - **Triggers**: on push to main, on pull_request (but only runs if core succeeded)
     - Use `needs: [core]` dependency or conditional step
   - **Jobs**:
     - **name**: Capability & Extras Tests
       - **runs-on**: ubuntu-latest
       - **continue-on-error**: true   # non-blocking
       - **strategy**:
         ```yaml
         matrix:
           python-version: ['3.11']   # reduced matrix to save time
           extras: [none, embeddings]
         ```
       - **steps**:
         ```yaml
         - uses: actions/checkout@v4
         - uses: actions/setup-python@v5
           with:
             python-version: ${{ matrix.python-version }}
         - name: Install dependencies
           run: |
             if [ "${{ matrix.extras }}" = "embeddings" ]; then
               pip install -e ".[test,embeddings]"
             else
               pip install -e ".[test]"
             fi
         - name: Run capability tests
           run: |
             pytest -m "capability" \
               --cov=eck --cov-append --cov-report=xml --cov-report=html \
               || echo "Capability tests failed (non-blocking)"
         - name: Optional local LLM smoke
           if: env.HAS_LLM_MODEL == 'true'   # set via env or skip if model not detected
           run: pytest tests/test_local_llm_smoke.py || echo "Smoke failed (non-blocking)"
           # Skips gracefully if no local LLM model detected (non-authoritative smoke)
         - name: Upload artifacts
           uses: actions/upload-artifact@v4
           with:
             name: capability-artifacts
             path: |
               htmlcov/
               coverage.xml
             retention-days: 7
         ```
   - **Enforcement**: Job failures → warning / notification / artifact upload only; does not block
   - Extras are always tested independently; core results never depend on extras and remain identical regardless of capability-layer matrix outcomes.
   - Non-blocking failures in capability layer MUST be summarized in artifacts (e.g., structured summary table or failure log excerpt) listing failed tests, reasons, and affected extras/matrix combinations for quick auditing.

4. **Shared Configuration & Best Practices**
   - Cache: `actions/cache` for `~/.cache/pip` and `.venv`
   - Artifacts: always upload coverage HTML + XML (even on failure)
   - Notifications: core failure → required status check; capability failure → comment or Slack (via action)
   - Badges: optional Codecov integration for core coverage only
   - Pytest config (`pytest.ini` / `pyproject.toml`):
     ```toml
     addopts = "--strict-markers --cov-fail-under=95 --cov=eck"
     ```
     - Markers defined: core, guardrail, memory, critic, policy, queue, capability
     - Core markers cannot be mixed with capability markers in a single invocation to prevent accidental coupling.

**Rationale & Architectural Alignment**

- Separate workflows preserve layer isolation (deterministic vs capability).
- `continue-on-error` + reduced matrix in capability layer keeps it non-blocking and cost-efficient.
- Core layer remains stdlib-only → zero external deps, fast, reproducible.
- Artifacts and coverage reporting support observability (Property 5).
- Enforcement aligns with TCB containment (Property 1) and formal-verifiability path (Property 12).

**Must Never Happen (Red Lines)**

- Core workflow depending on extras, real LLM, network calls, or external services.
- Capability failures blocking merge or release.
- Coverage enforcement disabled or threshold lowered without new ADR.
- Workflow YAML introducing runtime assumptions contradicting invariants (retries, timeouts affecting replay).
- Unified single workflow mixing deterministic and capability layers.
- Conditional logic in core workflow that indirectly depends on or reads capability-layer outputs or results.
- Reopening of ADR-034 or prior ADRs.
