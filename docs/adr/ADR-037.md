# ADR-037: CI Observability & Logging

**Status**  
LOCKED (semantic invariant for v0.2.0 core)

## Objective

Define the observability, logging, and artifact standards for the CI workflow established in ADR-034 and implemented in ADR-035/036.  

This ADR ensures all CI output is auditable, uses the canonical "eck-core" logger where applicable, produces structured artifacts, and maintains strict isolation between deterministic core logging and capability-layer output — without introducing runtime exceptions, sensitive data, or behavioral side-effects.

This ADR is scoped to the fourth (optional but recommended) step of A5 in the v0.2.0 roadmap (ADR-020). It builds directly on ADR-034–036 without reopening their decisions, emergent architectural properties (especially Property 5), the immutable "eck-core" logger invariant, or prior locked ADRs.

## Decisions

1. **Logger Usage**  
   - All test harnesses, custom scripts, and CI steps that emit structured logs **MUST** use `logging.getLogger("eck-core")` exclusively.  
   - **Core layer logs:** INFO level for test start/completion, WARNING for coverage near-threshold (with traceable test ID linked to artifacts for automated correlation), ERROR only for invariant violations.  
   - **Capability layer logs:** Same logger, but non-blocking and summarized in artifacts.

2. **Structured Output & Artifacts**  
   - **Required artifacts** on every core run (uploaded automatically):  
     - `junit.xml` (pytest JUnit XML for test results)  
     - `coverage.xml` + `htmlcov/` (pytest-cov reports)  
     - `eck-core.log` (structured JSON lines of all "eck-core" logger output, retained for last 30 runs to align with ADR-036 trend tracking)  
   - **Capability-layer summary table** (JSON preferred for automated auditing, CSV as fallback) with formal schema:  
     - `test_name` (string)  
     - `reason` (string)  
     - `extras` (string or null)  
     - `matrix_version` (string)  
     - `timestamp` (ISO string, always in UTC for global CI consistency)  
     - `version` (string, semantic versioning for the summary schema to ensure backward compatibility)  
   - Optional capability-layer artifacts retained for 7 days in GitHub Actions artifact storage only (external mirroring, e.g., Codecov, is optional and not part of this contract).  
   - If Slack or other notification integration is used for regression alerts, it **MUST** reference artifact URLs directly for traceability.

3. **Logging Constraints**  
   - No sensitive data (secrets, full prompt content, model outputs) may appear in any CI log or artifact.  
   - Logging failures (e.g., logger unavailable) **MUST NOT** raise exceptions, trigger HALT, or affect test execution — graceful degradation only (fallback to stderr with warning).  
   - Capability-layer logs **MUST NOT** influence core-layer pass/fail status.

## Rationale & Architectural Alignment

- Enforces observability before enforcement (Property 5) by making all CI signals auditable via the canonical "eck-core" logger.  
- Structured artifacts support end-to-end traceability (linking coverage, JUnit, and logs) without coupling layers.  
- No sensitive data and graceful degradation preserve refusal-over-fabrication posture and microkernel isolation.  
- Optional but recommended status respects the "last in roadmap" principle — CI observability enhances, but does not lead, stable semantics.

## Must Never Happen (Red Lines)

- Any CI log or artifact using a logger name other than "eck-core".  
- Logging failures causing exceptions, HALT, or test abortion.  
- Sensitive data (secrets, full prompts, model outputs) appearing in logs/artifacts.  
- Capability-layer logs or artifacts influencing core-layer pass/fail status.  
- Non-structured free-form logs for core invariant events (structured JSON lines required).  
- Reopening of ADR-034–036 or prior ADRs via logging configuration.
