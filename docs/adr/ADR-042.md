# ADR-042: Propose/Authorize/Perform Execution Boundary

**Status:** Proposed (Target: v0.3.0)

---

## Objective

Define the kernel-enforced execution boundary that separates LLM action proposals from real-world effects, replacing the current `execute_task` stub with a formally grounded propose/authorize/perform split.

This ADR establishes:

* the structure and authority of `ProposedAction`
* the contract for `propose_execution` (advisory)
* the contract for `authorize_and_perform` (kernel-enforced)
* the structure of `ExecutionResult` (structured refusal semantics)
* the invariants governing the execution boundary
* the relationship to the formal TLA⁺ model (ECK.tla)

This ADR fulfills the primary architectural gap identified in the v0.3.0 roadmap:

> The kernel currently has no authorization boundary between "LLM proposes an action" and "action is performed."

---

## Context

### Current State (Non-Compliant)

The current agent loop calls:

BACKTICKS
outcome = execute_task(task_text, self.llm)
BACKTICKS

This is non-compliant because:

* `execute_task` is a stub — in production use it will perform real-world effects
* there is no kernel-level authorization boundary between LLM proposal and effect
* the policy gate governs whether execution may occur at all, but nothing governs
  what the execution surface is permitted to do
* real-world effects can occur without a structured, inspectable proposal
* there is no second authorization check between "execution permitted" and
  "effect performed"

---

### Formal Grounding

The propose/authorize/perform split is formally grounded in the TLA⁺ model
verified in `docs/formal/ECK.tla`. TLC exhaustively verified the following
invariants across 79 distinct states:

* **INV1 NoEffectWithoutGateAuthorization** — `effect_performed => gate_authorized`
* **INV2 NoEffectWithoutKernelAuthorization** — `effect_performed => kernel_authorized`
* **INV3 NoEffectWithoutProposal** — `effect_performed => proposed_action = PROPOSED`
* **INV4 HaltFreezesKernelState** — once halted, all kernel state variables are frozen
* **INV5 PolicyEscalationIsMonotonic** — policy mode only advances, never retreats
* **INV6 GateAuthorizationRequiresNonHalt** — gate cannot open in HALT mode
* **INV7 GateAuthorizationMatchesPermission** — gate variables are always in sync

These invariants are non-negotiable red lines for this ADR. Any implementation
that violates them is non-compliant.

---

### Existing Vocabulary (Live Codebase)

The following types are already established in the live codebase and are used
throughout this ADR without modification:

* **`ExecutionMode`** (`eck/policy_gate.py`) — the per-cycle gate output enum:
  EXECUTE / RETRY / DEGRADE / HALT. This is the per-cycle decision, not the
  long-lived escalation state.
* **`PolicyDecision`** (`eck/policy_gate.py`) — the wrapper object returned by
  `PolicyGate.evaluate()`, carrying `mode: ExecutionMode`, `cause`, `reason`,
  and `rule_id`.
* **`PolicyContext`** (`eck/policy_gate.py`) — typed context passed to gate
  evaluation, including `safety_level`, `environment`, and
  `failure_window_active`.
* **`PolicyGate`** (`eck/policy_gate.py`) — base class for all policy gate
  implementations.
* **`PolicyMode`** (`eck/config.py`) — the long-lived escalation state:
  NORMAL / GUIDED / ENFORCED / HALT. Distinct from `ExecutionMode`.

This ADR introduces `ProposedAction` and `ExecutionResult` as new types.
All other references use the established vocabulary above.

---

### Two Orthogonal Authorization Questions

The formal model proves two orthogonal authorization questions must both be
answered affirmatively before any real-world effect may occur:

1. **Gate authorization** — may execution occur at all this cycle?
   Answered by `PolicyGate.evaluate()`, which returns a `PolicyDecision`.
   Only a `PolicyDecision` whose `mode is ExecutionMode.EXECUTE` permits
   effect. Gate refusal is not reducible to `PolicyMode` — the gate's inputs
   are `(proposed_action, confidence, context)`, not policy mode directly.
   Non-EXECUTE outcomes may occur independently of the long-lived system
   posture.

2. **Kernel authorization** — is this specific proposed action within the
   authorized envelope? Answered by `authorize_and_perform`. Governed by
   the kernel's action-level enforcement.

These are distinct and orthogonal. The policy gate does not authorize specific
actions. The kernel does not govern whether execution may occur at all. Neither
alone is sufficient.

---

### Key Design Questions

#### 1. ProposedAction Structure

What fields must a `ProposedAction` contain to be inspectable, auditable, and
policy-evaluable?

#### 2. ExecutionResult Structure

How should refusal be represented to preserve semantic distinction between
refused, failed, and no-op execution — preventing conflation in critic
classification and confidence updates?

#### 3. Execution Envelope

What constitutes the authorized execution envelope? What constraints does
`authorize_and_perform` enforce before performing effects?

#### 4. Side Effect Boundary

Where exactly is the boundary between advisory computation and real-world
effect? How is it enforced against accidental bypass via helper functions,
error handlers, or callbacks?

#### 5. Gate/Kernel Sequencing

How does the agent loop enforce that `authorize_and_perform` is only called
when `PolicyGate.evaluate()` has returned a `PolicyDecision` whose
`mode is ExecutionMode.EXECUTE` — preserving the two-gate proof?

#### 6. Proposal Parse Failure

What happens when `propose_execution` returns `None`? This is a per-cycle
no-op, not a system halt, and must be handled accordingly.

---

## Decision

### 1. ProposedAction Structure

`ProposedAction` is a structured, typed, kernel-inspectable object. It is
advisory — it carries no authority. It is produced by `propose_execution` and
consumed by `authorize_and_perform` and `PolicyGate.evaluate()`.

Required fields:

BACKTICKS
@dataclass(frozen=True)
class ProposedAction:
    action_type: str          # categorical action identifier
    parameters: dict          # structured action parameters
    task_text: str            # originating task text (context only)
    task_id: str              # correlation identifier
    provenance_id: str        # call identifier of the LLM call that produced
                              # this proposal — must be non-empty and
                              # correlatable to telemetry logs
BACKTICKS

`ProposedAction` MUST be:

* immutable (frozen dataclass or equivalent)
* fully serialisable to structured log
* inspectable by `PolicyGate` without side effects
* the only action-bearing input to `authorize_and_perform`

`ProposedAction` MUST NOT:

* contain executable code or callable objects
* grant authority by its existence

In compliant implementations, `ProposedAction` MUST be constructed via
`propose_execution` and not constructed directly in other code paths.

---

### 2. ExecutionResult Structure

`ExecutionResult` is a structured return type from `authorize_and_perform`
that preserves semantic distinction between performed, refused, and failed
execution. Downstream consumers must not conflate refused execution with
failed execution — `performed` is the authoritative signal.

BACKTICKS
@dataclass(frozen=True)
class ExecutionResult:
    performed: bool             # True iff a real-world effect was produced
    outcome: str                # outcome string for critic evaluation
                                # (empty if not performed)
    refusal_reason: str | None  # populated when performed=False;
                                # None when performed=True
BACKTICKS

* `performed=True` — effect was produced; `outcome` carries the result;
  `refusal_reason` is None
* `performed=False` — no effect produced; `outcome` is empty;
  `refusal_reason` identifies why

---

### 3. propose_execution Contract

BACKTICKS
def propose_execution(
    task_text: str,
    llm_call: Callable[[str], str],
) -> ProposedAction | None
BACKTICKS

* calls the LLM to generate a structured action proposal
* parses and validates the response into a `ProposedAction`
* returns `None` if the LLM response cannot be parsed into a valid proposal
* MUST NOT perform any real-world effects
* MUST NOT consult the policy gate
* is advisory only — its output has no authority until authorized

A `None` return is a per-cycle no-op. It MUST NOT be interpreted as a system
halt or escalation signal.

---

### 4. authorize_and_perform Contract

BACKTICKS
def authorize_and_perform(
    proposed_action: ProposedAction,
    policy_mode: PolicyMode,
) -> ExecutionResult
BACKTICKS

* is the **sole function permitted to produce real-world effects**
* MUST raise `AssertionError` if `proposed_action` is None (INV3) — a None
  argument is an invariant violation indicating a non-compliant caller
* MUST raise `AssertionError` if `policy_mode` is `PolicyMode.HALT` (INV6) —
  a defensive invariant check; primary gate authorization is enforced by the
  agent loop sequencing
* enforces kernel authorization of the specific action — validates
  `action_type` and `parameters` against the authorized envelope
* performs the effect only when all preconditions and kernel authorization
  are satisfied
* returns `ExecutionResult` in all cases for contract-level authorization
  failures — never raises for authorization failures
* ALL external side effects MUST occur exclusively inside this function,
  including transitive calls

In compliant implementations, `authorize_and_perform` MUST only be invoked
from the agent loop execution phase, and only when `PolicyGate.evaluate()`
has returned a `PolicyDecision` whose `mode is ExecutionMode.EXECUTE` for
the current cycle.

**There must be no alternate code path — including error handling, retries,
or callbacks — that can produce external side effects outside
`authorize_and_perform`.**

---

### 5. Authorized Execution Envelope

`authorize_and_perform` enforces the following kernel-level constraints before
performing any effect:

* `policy_mode` is not HALT (defensive invariant check — INV6)
* `action_type` is within the registered action whitelist
* `parameters` conform to the schema for the declared `action_type`
* `provenance_id` is present and non-empty
* `task_id` matches the current active task *(deferred — see thin-slice note below)*

Failure to satisfy any enforced constraint MUST result in a refused
`ExecutionResult` with `performed=False` and a populated `refusal_reason`.
No effect is produced.

Note: the action whitelist and parameter schemas are deployment-specific and
constitute the first real capability surface of the kernel. They are not
defined by this ADR and must be provided per deployment context.

---

### 5a. Thin-Slice Implementation Note

The first implementation of `authorize_and_perform` (v0.3.0 initial slice)
enforces a subset of the full execution envelope. This is an explicit,
intentional deferral — not non-compliance.

**Enforced in the thin slice:**

* `proposed_action is not None` (INV3 — hard invariant, raises on violation)
* `policy_mode != PolicyMode.HALT` (INV6 — defensive invariant, raises on violation)
* `action_type` is within the registered action whitelist
* required parameter keys are present for the declared `action_type`
* `provenance_id` is non-empty

**Deferred from the thin slice:**

* Active-task context verification (`task_id` matches current active task) —
  deferred because `authorize_and_perform` has no access to active task
  context in the current architecture. Will be addressed when the execution
  context object is formalised in a subsequent slice.
* Full parameter schema validation (type and value constraints beyond key
  presence) — deferred to when deployment-specific schemas are defined.

**Thin-slice action whitelist:**

* `"llm_query"` — calls the LLM with a `prompt` parameter; proves the boundary
  can carry a real action with an execution result
* `"no_op"` — produces no external effect; proves the boundary can carry a
  structured action with no side effect

Both actions are sufficient to validate the boundary mechanics end-to-end.
`"llm_query"` in the thin slice produces another LLM call rather than a
genuinely effectful surface (filesystem, API, tool). This proves the
boundary contract without introducing external dependencies prematurely.

---

### 6. Agent Loop Integration

The agent loop MUST enforce the two-gate authorization sequence explicitly.
`authorize_and_perform` MUST only be called when `PolicyGate.evaluate()`
has returned a `PolicyDecision` whose `mode is ExecutionMode.EXECUTE`. This
aligns with the existing pattern in `eck/agent_loop.py` where `decision.mode`
is inspected before any execution hook is called.

BACKTICKS
# Step 1: Propose (advisory — no effects)
proposed = propose_execution(task_text, self.llm)

# Step 2: Handle no proposal — per-cycle no-op, not a halt
if proposed is None:
    result = ExecutionResult(
        performed=False,
        outcome="",
        refusal_reason="no_valid_proposal",
    )
else:
    # Step 3: Gate check (may execution occur at all this cycle?)
    decision: PolicyDecision = self.policy_gate.evaluate(
        proposed_action=proposed,
        confidence=self._confidence.get_value(),
        context=policy_context,
    )

    # Step 4: Kernel authorization and effect (only when gate returns EXECUTE)
    if decision.mode is ExecutionMode.EXECUTE:
        result = authorize_and_perform(
            proposed, self.current_policy_mode
        )
    else:
        result = ExecutionResult(
            performed=False,
            outcome="",
            refusal_reason=f"gate: {decision.mode.name}",
        )

outcome = result.outcome
BACKTICKS

This sequencing preserves INV1 and INV2: no effect occurs without both gate
authorization (a `PolicyDecision` whose `mode is ExecutionMode.EXECUTE`) and
kernel authorization (action-level check inside `authorize_and_perform`).

The previous `execute_task(task_text, self.llm)` call MUST be removed.
`execute_task` MUST be retired.

---

### 7. PolicyGate Integration

`PolicyGate.evaluate()` MAY inspect `ProposedAction` to determine whether
execution should be permitted at the cycle level. It MUST NOT perform
action-level admissibility checks — that responsibility remains exclusively
within `authorize_and_perform`.

`PolicyGate` MUST:

* be side-effect free
* return a `PolicyDecision` with `mode: ExecutionMode`
* not trigger or authorize execution directly

Gate refusal is not reducible to `PolicyMode` — the gate's inputs are
`(proposed_action, confidence, context)`, not policy mode directly.
Non-EXECUTE outcomes may occur independently of the long-lived system
posture. Only a `PolicyDecision` whose `mode is ExecutionMode.EXECUTE`
permits the agent loop to call `authorize_and_perform`.

---

### 8. Formal Invariant Enforcement

Runtime invariant violations MUST raise `AssertionError` at the implementation
boundary — not be silently swallowed or returned as `ExecutionResult`:

* `proposed_action is not None` at entry to `authorize_and_perform`
  (INV3) — invariant violation, non-compliant caller
* `policy_mode != PolicyMode.HALT` at entry to `authorize_and_perform`
  (INV6) — defensive invariant check

Note: explicit `raise AssertionError(...)` is used rather than `assert`
statements, which can be stripped by Python's `-O` optimization flag.

The agent loop enforces INV1 by only calling `authorize_and_perform` when
`decision.mode is ExecutionMode.EXECUTE`. Contract-level authorization
failures (whitelist, schema, provenance) return refused `ExecutionResult`
and do not raise.

---

### 9. Observability Requirements

`authorize_and_perform` MUST emit structured log entries for:

* authorization decision with `performed` field
* `refusal_reason` when `performed=False`
* `action_type`, `task_id`, and `provenance_id` on every call
* `outcome` string when `performed=True`

`propose_execution` MUST emit structured log entries for:

* successful proposal construction with `action_type` and `task_id`
* parse failure with response preview

All log entries MUST be structured and consistent with ADR-037.

## Non-Goals

This ADR does NOT define:

* the specific actions available in the whitelist (domain-specific, defined
  per deployment)
* the demonstration policy module (separate ADR)
* the telemetry schema (separate ADR, gated behind this ADR)
* confidence signal dynamics (ADR-021–025)
* drift monitor mechanics (ADR-040)

## Consequences

### Positive

* closes the primary architectural gap — no effect without both gate and
  kernel authorization
* `ProposedAction` is now a real semantic object inspectable by `PolicyGate`
* `ExecutionResult` preserves semantic distinction between refused, failed,
  and no-op execution
* `ExecutionMode` and `PolicyMode` remain distinct — no conflation of
  per-cycle output with long-lived escalation state
* execution boundary is formally grounded and machine-verified
* audit trail is complete — every authorization decision is logged
* enables meaningful domain-specific policy modules

### Trade-offs

* introduces structured action proposal overhead on every execution cycle
* requires action whitelist maintenance per deployment
* `propose_execution` may return `None` on LLM parse failure — agent loop
  handles as per-cycle no-op
* `ExecutionResult` requires downstream consumers to use `performed` to
  distinguish refusal from failure

## Test Requirements

### 1. No Effect Without Proposal (INV3)

* `propose_execution` returns `None`
* agent loop proceeds

→ `authorize_and_perform` MUST NOT be called
→ `ExecutionResult(performed=False, refusal_reason="no_valid_proposal")`
  returned

### 2. No Effect Without Gate Authorization (INV1)

* `PolicyGate.evaluate()` returns a `PolicyDecision` whose `mode` is
  `ExecutionMode.RETRY`, `ExecutionMode.DEGRADE`, or `ExecutionMode.HALT`

→ `authorize_and_perform` MUST NOT be called
→ `ExecutionResult(performed=False, refusal_reason=f"gate: ...")` returned

### 3. HALT Mode Invariant Check (INV6)

* `authorize_and_perform` called directly with `policy_mode=PolicyMode.HALT`
  (non-compliant caller — invariant violation)

→ MUST raise `AssertionError` at entry — this is an invariant violation,
  not a normal refusal path

### 4. No Effect Without Kernel Authorization (INV2)

* `action_type` not in whitelist
* `authorize_and_perform` called after gate returned
  `ExecutionMode.EXECUTE`

→ `ExecutionResult(performed=False, refusal_reason=...)` returned — no
  effect produced

### 5. No Alternate Side-Effect Path

* error handler, retry, or callback invoked during execution
* `authorize_and_perform` has refused

→ MUST NOT produce external side effects

### 6. ExecutionResult Semantic Distinction

* `authorize_and_perform` refuses (contract-level)

→ `performed=False`, `refusal_reason` populated, `outcome` empty

* `authorize_and_perform` succeeds

→ `performed=True`, `outcome` populated, `refusal_reason` None

### 7. Proposal Is Immutable

* attempt to mutate `ProposedAction` after construction

→ MUST raise (frozen dataclass enforcement)

### 8. Observability — Authorization

* `authorize_and_perform` called with valid proposal and gate decision

→ structured log entry emitted with `action_type`, `task_id`,
  `provenance_id`, `performed`

### 9. Observability — Refusal

* `authorize_and_perform` refuses

→ structured log entry emitted with `refusal_reason`

### 10. PolicyGate May Inspect ProposedAction

* `PolicyGate.evaluate()` receives `ProposedAction` and returns a
  `PolicyDecision` whose `mode` is not `ExecutionMode.EXECUTE`

→ agent loop MUST NOT call `authorize_and_perform`

### 11. Deterministic Replay

* identical `ProposedAction` and policy state

→ identical `ExecutionResult`

### 12. No-Proposal Is Not A Halt

* `propose_execution` returns `None` three consecutive cycles

→ `PolicyMode` MUST NOT escalate as a result
→ agent loop continues normally

---

## Compliance

Any implementation that:

* produces external side effects outside `authorize_and_perform`
* calls `authorize_and_perform` without a valid `ProposedAction`
* calls `authorize_and_perform` when `PolicyGate.evaluate()` has not returned
  a `PolicyDecision` whose `mode is ExecutionMode.EXECUTE`
* permits effects when `policy_mode` is `PolicyMode.HALT`
* permits effects when `action_type` is not in the whitelist
* allows `PolicyGate` to perform action-level admissibility checks
* conflates refused and failed execution in `ExecutionResult`
* maps proposal parse failure to system halt or `PolicyMode` escalation
* retains `execute_task` without replacing it with the propose/authorize/perform
  split
* uses `PolicyMode` values where `ExecutionMode` values are required

is **non-compliant** with this ADR.
