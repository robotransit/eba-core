# ADR-038: Policy Gate Contract – Exclusive Consumer of Epistemic Signals

**Status:** Contract-Locked for Implementation (v0.2.0 core)

---

## Context

The policy gate (G_p) is the only component in the ECK/ESS architecture allowed to map epistemic signals (e.g. confidence) into control decisions. This boundary enforces Invariant I1 (Epistemic Isolation):

> No other component may branch, gate, or alter control flow based on confidence.

All other parts of the kernel are deterministic mechanisms that preserve signal isolation. The policy gate is the sole location where domain-specific control semantics are applied.

---

## Decision

We define a minimal, strict contract for the policy gate.

---

## Temporal Placement (Execution Boundary)

The policy gate operates as a **pre-execution authorization boundary** in the agent loop.

- The gate evaluates a proposed action before any execution occurs  
- No action may be executed unless authorized by the gate  
- All returned decisions are pre-execution control outcomes, not post-hoc evaluations  

Execution modes have the following semantics:

- **EXECUTE** → authorize execution of the proposed action  
- **HALT** → forbid execution in the current cycle  
- **RETRY** → forbid execution of the current proposal and require a new proposal cycle  
- **DEGRADE** → forbid execution of the current proposal as-is and require a separately defined degraded path  

The gate does not execute actions and does not perform recovery itself.

---

## Policy Gate Invariants

The gate must satisfy the following invariants:

### 1. Exclusive Consumer (Invariant I1)

The gate is the only component allowed to consume confidence for control decisions.  
No other component may branch, gate, or alter control flow based on confidence.

---

### 2. Pure Function Requirement

The gate must be a pure, referentially transparent function of (proposed_action, confidence, context).

- No internal mutable state across evaluations  
- No randomness  
- No hidden or implicit inputs  

---

### 3. Determinism

For identical (proposed_action, confidence, context), the gate must return identical PolicyDecision.

---

### 4. Side-Effect Free

The gate must not:

- mutate external state  
- perform I/O  
- call external systems (including LLMs)  

---

### 5. Confidence Validation

The gate must validate that confidence is:

- numeric (int or float, excluding bool)  
- within the closed interval [0.0, 1.0]  

Invalid inputs must raise an error.

---

### 6. Monotonicity

For fixed proposed_action and fixed context, lower confidence must not produce a more permissive decision.

Execution modes are ordered by restrictiveness:

HALT > RETRY > DEGRADE > EXECUTE  

where “>” denotes “more restrictive than”.

Formally:

    if c1 < c2:
        mode(c1) ≥ mode(c2)

with respect to the defined execution ordering.

Monotonicity must be testable via unit tests.

---

### 7. Single Gate Instance

Exactly one policy gate is active per kernel instance.

---

### 8. Startup Selection Only

Gate selection occurs at startup.  
Runtime hot-swapping is not permitted in v0.2.0.

---

### 9. Explicit Default Semantics

The system must always have a defined policy gate.

Disabling the configured gate must fall back to:

- a defined default gate, or  
- explicit HALT behavior  

No implicit “no-op” behavior is allowed.

---

### 10. Context Isolation

The gate may only depend on the provided PolicyContext.  
No implicit or external context may influence decisions.

---

## Minimal Contract Types

```python
from enum import Enum
from typing import NamedTuple, Any


class ExecutionMode(Enum):
    EXECUTE = "EXECUTE"
    RETRY   = "RETRY"
    HALT    = "HALT"
    DEGRADE = "DEGRADE"


class PolicyCause(Enum):
    FAILURE_WINDOW = "FAILURE_WINDOW"
    CONFIDENCE     = "CONFIDENCE"
    SAFETY         = "SAFETY"
    DEFAULT        = "DEFAULT"


class PolicyContext(NamedTuple):
    user_id: str | None = None
    safety_level: str | None = None
    environment: str | None = None
    failure_window_active: bool = False


class PolicyDecision(NamedTuple):
    mode: ExecutionMode
    cause: PolicyCause
    reason: str
    rule_id: str  # MUST be non-empty, machine-stable identifier
```

---

## Policy Gate Interface

```python
class PolicyGate:
    def evaluate(
        self,
        proposed_action: Any,
        confidence: float,
        context: PolicyContext
    ) -> PolicyDecision:
        raise NotImplementedError("Subclasses must implement evaluate()")
```

---

## Action Handling (Opaque by Contract)

proposed_action is opaque to the gate contract; the gate may interpret it only according to domain-specific rules.

- The contract does not define its structure  
- The default gate does not inspect proposed_action  

This preserves abstraction while allowing domain-specific policy specialization.

---

## Recovery Semantics (Boundary Definition)

The policy gate defines decision outcomes, not recovery execution.

- **RETRY** → current action must not execute; a new proposal cycle is required  
- **DEGRADE** → current action must not execute as-is; execution may proceed only via a defined degraded path  
- **HALT** → no action is executed  

State reset, retry orchestration, and degraded execution are responsibilities of the surrounding control loop, not the gate itself.

---

## Rule Identifier Requirement (Normative)

rule_id is mandatory for every PolicyDecision.

- It must be non-empty  
- It must be machine-stable  
- It must identify the rule that produced the decision  

---

## Rationale

Mandatory rule_id ensures:

- Auditability — decisions can be traced to specific rules  
- Deterministic traceability — identical inputs yield identical rule provenance  
- Testability — tests can assert which rule fired  
- Observability — logs can be aggregated without parsing free text  
- Extensibility — enables future policy analysis and tuning  

Allowing rule_id to be optional would degrade these guarantees and introduce ambiguity.

---

## Consequences

- The gate is the sole control surface for uncertainty  
- Advisory-only semantics are strictly enforced  
- Control logic is centralized, deterministic, and auditable  

Every decision includes:

- execution mode  
- cause  
- reason  
- rule identifier  

- Monotonicity ensures predictable and testable behavior  
- Confidence validation prevents invalid inputs  
- The kernel remains minimal and stable  
- Domain-specific policies can be implemented without modifying kernel invariants  

---

## Alternatives Considered

- Hot-swappable gates — rejected for v0.2.0 (runtime complexity, state transition risks)  
- Multiple or composable gates — rejected for v0.2.0 (ordering ambiguity, conflict resolution)  
- LLM-backed gate logic — rejected for initial design (non-determinism, coupling risk)  
- Optional rule identifiers — rejected (breaks auditability, testability, and deterministic traceability)  
- Implicit or absent policy gate — rejected (violates epistemic isolation invariant)

## Summary

This ADR establishes the policy gate as a pre-execution, deterministic, pure, and exclusive decision boundary for mapping epistemic signals into control outcomes.

It enforces full auditability through mandatory rule identifiers and preserves all core ECK/ESS invariants while enabling safe, domain-specific policy specialization.
